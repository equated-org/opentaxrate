Design plan · built · main after 392c161 · 2026-10-22

Keep every source's own jurisdiction ids

Each state's rate source names its jurisdictions with its own codes, like Alabama's locality code 9454 for Montgomery or Washington's SER code 01726 for Seattle, and the ingest throws most of them away. This plan keeps them in one table, sales_tax_jurisdictions, and returns them on every part exactly as the publisher wrote them. That makes the answer as complete as the data we load, with no per-state mapping code.

Traced from src/ingest/load.ts, sst-files.ts, missouri.ts, states/*.ts, src/rates/index.ts, ranges.ts, map.ts, names.ts, reporting.ts, and the cached source files in /tmp/otr-cache (Alabama taxrates.csv, Illinois ordmache, Missouri's boundary CSV and rate workbook, the Streamlined files), on 2026-10-22.

Why keep the source's ids

A seller charges the rate, then files it. The filing side needs the codes the state uses for each jurisdiction, and the people the tax goes to. Most of that is already in the files we download: Alabama's rate file says Montgomery is locality 9454 and that the city collects its own tax (Administered: SELF). Today we read those columns, use them to find a Census FIPS code, and drop them. The answer then says 01:51000, which no Alabama form asks for.

The decision is to pass through, not map. Each ingest keeps a jurisdiction's name and every identifier column its source gives, keyed by the publisher's own column name, in a new table. A lookup joins its parts to that table and returns the ids unchanged. The per-state mapping layer built on 2026-10-22 (reporting.codes, missing, status, PART_CODES, OWN_CODE) goes away, and reporting shrinks to the agency and form directory, which is static and correct.

  • Complete for what we load. Every id a source publishes reaches the caller, in every state at once, instead of the seven states a hand-written mapping covered.
  • Nothing to verify. The API repeats the file, so there is no claim like "this is the return's code" that someone has to check state by state.
  • It's what the one competitor with codes does. Of the four services in artifacts/bench/answers, only Zip-Tax returns codes, in one jurTaxCode field per jurisdiction, and they are visibly each source's own: ALDOR locality codes (Birmingham 9137), Illinois location codes with the check digit (Pekin 90-0001-1), Washington's DOR location code (SeaTac 1733), Texas TAIDs, Arizona region codes (MAR), New York's Pub 718 code (HE 2121), Census FIPS elsewhere (Georgia 037), and null for about half of local parts. Avalara returns generic names ("WA CITY TAX"), TaxJar county and city names, Lovat only the total.
  • Not complete for filing everywhere. The Streamlined rate files have no names and only FIPS codes, so Georgia, Ohio and North Carolina still get no return code. Closing that gap means loading one more official file per state (Minnesota's tax type codes, Georgia's ST-3 chart), passed through the same way. That's out of scope here.

The model

A jurisdiction row describes one of the publisher's codes, keyed exactly like the rate rows: state, the publisher's type, and its code. A part's code is already type:code, so the join needs no translation. Ids that belong to a whole location rather than one jurisdiction, like Washington's SER code, which covers the state and Seattle together, stay on the area, in an ids column that replaces this week's reporting_code. Figure 1 shows both.

CREATE TABLE sales_tax_jurisdictions (
  state  text  NOT NULL,
  type   text  NOT NULL,            -- the rate row's type: 00, 01, x, kx, spd, 99 …
  code   text  NOT NULL,            -- the rate row's code, verbatim

  ids    jsonb NOT NULL DEFAULT '{}',  -- publisher column name → value, strings only
  file   text  NOT NULL,            -- the release it came from, e.g. "taxrates.csv"
  PRIMARY KEY (state, type, code)
);

Rules

  • The publisher's words, unchanged. An id's key is the source's own column or field name (Locality Code, RegionName, SPD_Type) and its value is the string the file has, leading zeros and all. No renaming, no reformatting, no inferred values.
  • Identity only. Ids are the fields that say which jurisdiction this is and who runs it: codes, names, the collecting agency. Fields that vary row by row for the same jurisdiction, like Alabama's TaxType or Rate Type, are not ids. Where an identity field differs between rows, take the value on the general sales row the rate came from.
  • Same key as the rate. A jurisdiction row exists only for a (state, type, code) some rate row has, and is written in the same transaction as the state's rates, so a lookup never sees ids from another release.
  • Absent means the source has none. ids is always present on a part, and {} means the source published no ids for it. A Census FIPS is never added as an id; it's already in code.
  • Names fall back, ids don't. A part's name is the jurisdiction's name, else the outline's name (sales_tax_shapes, as nameParts does today). Ids come only from the source.
  • Location ids only when settled. locationIds is the matched area's ids when every area the address could be in has the same ids, else {}, the way locationCode is null when areas differ.

What to reload after phases 1 and 2

Not everything. The source files under artifacts/ don't change; only what's read from them does.

  • Phase 1: nothing. migrate copies each reporting_code into ids before dropping the column. (On the dev database on 2026-10-22 every reporting_code was still null: no Streamlined state had been reloaded since 0006 added it. To get Washington's and Kansas's codes there, run refresh WA KS --force; that was already true before this plan.)
  • Phase 2: the map-read states and Missouri. sales_tax_jurisdictions fills only as a state loads. Until then lookups are unchanged, and in phase 3 parts would show ids: {} and Census names. pnpm refresh AL TX IL LA AZ NM CO AK VA MT SC FL HI ID MS NY PA MO reloads them, without --force: refresh fetches map-read states and Missouri on every run. Their GIS and API responses aren't archived, so this downloads again.
  • The 24 Streamlined states: nothing. Their rate files carry no names or ids.
  • Published snapshot. scripts/snapshot.sh now lists sales_tax_jurisdictions among its tax tables. Publish a new dump after the reload to include it. Older dumps still restore, and migrate brings them up to date.

Open questions

  • Should ids be dated? Recommend no. Names and codes rarely change, and the newest load replaces them with the rates; a dated rate on an old date then shows today's ids. Add starts_on/ends_on only if a source is found renumbering.
  • Should keys be the raw column names or tidied ones? Recommend raw (Locality Code, locat_cdr), which is the point of the change; the docs page lists each source's keys so a caller knows what to read.
  • Should Washington's SER code be returned as the DOR's four digits (1726)? Recommend raw 01726 in locationIds, with the docs saying Washington's location code is the SER code without its leading zero. It stays a pass-through, and the check against the DOR's lookup (205 of 221 addresses) is recorded there.
  • Where do Streamlined special districts get names? Nowhere in the files we load; leave them null. A later plan can load a state's own district list (Washington publishes one with location codes) as another source, passed through the same way.
  • Keep locationCode? Recommend yes for now; it's in use by callers. Mark it in the docs as OpenTaxRate's own geography key, not a filing code.

Appendix: words and concepts this page assumes

A part's type:code

The publisher's jurisdiction type and code, as stored on the rate row. Streamlined types are numbers (45 state, 00 county, 01 city); map-read states use their own (x an exclusive area, kx a district inside one).

"01:63000"            → type 01, code 63000 (Seattle's place FIPS)
"kx:2227016>3227999" → type kx, code 2227016>3227999 (Austin, Capital Metro)

Composite SER Code

Column 21 of a Streamlined boundary line: a code the state gives each combination of jurisdictions. Washington fills it with its DOR location code, zero-padded; Kansas with its own jurisdiction code; most states leave it blank.

A,…,PINE,ST,…,SEATTLE,98122,0017,,,,,01726,53,53,,63000,…
                                        ^ c[21] = "01726"  (DOR location 1726)

Alabama locality code and Administered

ALDOR's own number for each city and county that levies a tax, and who collects it: STATE (ALDOR), SELF (the locality), or a private collector such as AVENU.

Locality Code,Locality Name,County Number,TaxType,Rate Type,Administered,…,Rate
9454,MONTGOMERY,51,CU,GENER,SELF,20081101,,3.5

Texas TAID

The Comptroller's seven-digit taxing authority id; the first digit is the kind (2 city, 3 transit, 4 county, 5 or 6 special purpose district). Already the part code in Texas.

city 2227016 · transit 3227999 · county 4227001

jsonb ids

A Postgres JSON object column. It holds a source's identity fields without one column per state, and compares by value, so it can sit in the areas' unique key.

select ids->>'Locality Code' from sales_tax_jurisdictions
 where state = 'AL' and type = '01' and code = '51000';   -- 9454

describeParts

The proposed replacement for nameParts: one query for the parts' jurisdiction rows, one for outline names where a row has none.

part.name = row?.name ?? shapeName ?? null
part.ids  = row?.ids ?? {}
