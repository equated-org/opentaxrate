Design plan · built on branch debug-rates, not deployed · 2026-10-22

API keys unlock the outside geocoders

Without a key, a lookup may only ask the geocoders we run on spark-3: Photon and Pelias. A key unlocks every configured provider: Census, Nominatim, Geocodio, Mapbox, Esri, Google and Jev. Keys come from a dashboard you sign in to with a code sent to your email (Better Auth's email OTP, no OAuth), so every key belongs to a verified address. Every keyed lookup becomes one row in api_requests, a single Postgres table that is the user's query history, their answer cache and the meter that pricing will read later.

Traced from src/server.ts, src/lookup.ts, src/limits.ts, src/cache.ts, src/geocoding/registry.ts, locator.ts, budget.ts, src/standardize/index.ts, src/rates/streets/correct.ts and jev.ts, landing/cloudflare/worker.js, deploy/, and Better Auth v1.6 docs (fetched 2026-10-22). Nothing is built yet.

Why two tiers

Today every lookup on api.opentaxrate.com can reach every provider the server has a credential for. geocoderProviders() reads the environment and returns all of them, and nothing about the request changes that list. An anonymous visitor on the landing page can make the server call Mapbox, Esri or Google, which costs money and uses up their daily caps. The per-IP limit of 10 a minute and 300 a day slows this down but doesn't stop it.

The decision is to decide on each request which providers it may use, and to tie the paid ones to an identity. A request with no key gets the public tier, which may only ask the geocoders we host ourselves. A request with a valid key gets the keyed tier, which may ask every configured provider. The tier becomes one value, an Access, that lookUpRate() passes to the three places that call outside services: the locator's provider list, the Geocodio standardizer and Jev's street picker.

  • Why per request, not per deployment. One API serves both the free landing page and paying callers. A second deployment would mean two databases and two caches, with no shared caps.
  • Why Better Auth. It runs in the Hono process we already have, stores its tables in the same Postgres through the Drizzle adapter, and comes with both pieces we need as plugins: emailOTP for sign-in by code and @better-auth/api-key for hashed keys with per-key rate limits and quotas. A hosted service like Clerk would mean another vendor and another bill for something this small.
  • Why a bad key is an error. A revoked or mistyped key gets a 401, not a quiet fallback to the public tier. A paying caller who got public answers without noticing would see more refusals and never know why.
  • Out of scope. OAuth, passwords, teams and organizations, subscriptions and invoices. Paying is prepaid credit: the ledger ships in phase 2, buying through Stripe Checkout in phase 3.

What the public tier gives up

Expect more refusals on the public tier, and measure them before switching it on. The locator only accepts a point when two independent datasets agree within their margins. Photon is OpenStreetMap, and Pelias returns OpenStreetMap or OpenAddresses records. When both return OSM records, they count as one dataset. The lookup then goes down the single-dataset path, which accepts the point only if it falls inside the typed city's outline, and otherwise refuses. Today the cheap pair is usually Census (TIGER) and Nominatim (OSM), which are two different datasets. Phase 1 adds a bench run comparing the two tiers on the same cases, so the cost of the change is a measured number before it ships.

Rules

  • No key, no outside geocoder. The registry filters the list itself: geocoderProviders(policy) never returns a provider the policy doesn't allow, so the route can't forget to check.
  • One list names everything that costs. Provider ids are the registry's (census, nominatim, photon, pelias, geocodio, smarty, mapbox, here, esri, google) plus jev. The standardizer runs only when geocodio is allowed.
  • A key is either valid or a 401. A request that sends a key never falls back to the public tier.
  • Master keys are for you, not customers. OPENTAXRATE_MASTER_KEYS="equated=otr_master_…,test=otr_master_…" names one or more keys. Each needs the otr_master_ prefix and at least 32 random characters, or the server refuses to start. A match, compared in constant time on SHA-256 digests, gives the keyed tier with master: true: every provider, no credit, no allowance, no per-IP or per-key limit. The vendor caps in geocoder_usage still bound what it can spend. Its lookups are logged and cached in api_requests under key_id = 'master:equated', so its cost shows up next to everyone else's. Rotating means adding the new key, switching the app over, then removing the old one. Two keys can be live at once. The key is never logged and never accepted from the landing Worker's forwarded requests.
  • Only verified accounts hold keys. Signing in with an email code sets emailVerified. A before-hook on /api-key/create refuses any session whose user isn't verified, so a later sign-in method can't get around it.
  • One table is the history, the cache and the meter. A keyed lookup first looks for the user's own 200 row with the same answer_key from the last 24 hours. Only the tax answer is stored; a traced lookup's geocoder points and outlines are dropped, and traced lookups are never answered from history. Hit or miss, it then appends one row, and a hit is marked cached with no cost. The dashboard's history, the month's totals and later billing all read these rows. Nothing else stores keyed answers.
  • Caches never cross tiers or users. The in-memory AnswerCache only holds and serves public answers. A user's cached answers are found by their own user_id. Cached geocoder points are already safe, because the locator reads cached rows only for the providers it was given.
  • Rows are kept 90 days. A daily DELETE FROM api_requests WHERE at < now() - interval '90 days' (on start and every 24 hours) keeps the table bounded. Ninety days covers a full billing month after it closes. Answers asked with include=trace are stored with their outline geometry, which makes those rows larger.
  • No account costs more than it pays. A paid geocoder is asked only when the account's allowance (80% of what it has paid) covers the call. Stripe's fee and hosting come out of the other 20%. See What a keyed lookup costs us.
  • Vendor caps are shared. postgresGeocodeBudget still caps each credential across every caller. A key's quota limits that key, and the vendor cap limits all of us.
  • Snapshots never carry accounts. scripts/snapshot.sh dumps an explicit --table list, so the new tables are left out without any change. A test keeps it that way.
  • Self-hosting is unchanged by default. With nothing set, every provider is public and /api/auth isn't mounted.

The locator already records each provider's outcome in its GeocodeTrace ("matched", "skipped" and so on). Phases

Three pull requests. Phase 1 stops the public API from spending. Phase 2 is every migration plus accounts, keys, the dashboard and the credit ledger, with the 100-lookup trial as the only way to get credit. Phase 3 adds buying credit through Stripe. Each phase is safe to ship alone: after phase 2, a key that runs out of credit gets a 402 and nobody can spend past what they hold.

What a keyed lookup costs us

The figures come from the measured mix on /benchmarks: 309 random addresses with every provider on, at the vendors' published prices (checked 2026-10-22), once every free tier is used up. Per 1,000 keyed lookups, geocoding costs $1.14, and Jev adds at most $0.12. Stripe takes 2.9% + $0.30 of each top-up, which is 5.9% of a $10 top-up and 3.5% of $50. In the benchmark, 5.5% of addresses were declined, and declines aren't charged.

$1.50$1.33+$0.19+$0.07

Averages hide the risk. One lookup that asks every paid provider costs about $0.0112: Geocodio, its ZIP+4 lookup, HERE, Mapbox, Esri, Google, Smarty and Jev together. That's almost 6 times a $0.00195 charge. A customer whose addresses are mostly hard ones (rural, new builds, near city lines) loses money at any flat price. Two rules make break-even hold for every account, not just on average:

  • A geocoder allowance per account. Each charged lookup adds 80% of its price to the account's geo_allowance_micros. A paid provider is asked only if the allowance covers its cost, and the cost comes out of it. Free providers are always asked. So no account's geocoder spend can exceed 80% of what it paid, and the other 20% covers the Stripe fee (at most 5.9%) and leaves the rest for hosting. An account of mostly easy addresses builds a pool that pays for its occasional hard one.
  • A price that keeps typical accounts above the floor. At $1.50, the allowance grows by $1.13 per 1,000 lookups but the average spend is $1.14–1.26, so an average account would slowly run dry and lose the paid geocoders. At $1.95 it grows by $1.47, which covers the average with room to spare. $1.95 is still about a twelfth of Zip-Tax's per-call price past its plan ($0.0242) and 1/25th of Stripe Tax's ($0.05).

Below the vendors' free tiers (Geocodio's 2,500 a day, Mapbox's 100,000 a month, Google's 10,000 a month) the real cost is close to $0, so small accounts are nearly all margin. The allowance still counts list prices, so the guarantee doesn't depend on free tiers lasting. Registry costs must match list prices for the allowance to be right, so phase 2 corrects the defaults (Geocodio $0.001 and its ZIP+4 lookup $0.002, HERE $0.00083, Mapbox $0.00075, Esri $0.0005, Google $0.005).

Phase 2: accounts, keys, the dashboard and the credit ledger

Email-code sign-in, API keys, keyed lookups with every provider, the api_requests history and cache, the Home, API keys and History screens, and the token ledger. One migration holds every table and column this plan needs, so phase 3 is code only. New accounts get 100 lookups of credit. At zero, a key gets a 402 until buying opens.

  1. Migration 0005_accounts.sql. It adds Better Auth's user, session, account, verification and apikey, from npx @better-auth/cli generate into src/db/auth-schema.ts. user gets three extra fields, which the client can't set: credit_micros bigint, geo_allowance_micros bigint and stripe_customer_id text. It also adds api_requests as specified above, plus charged_micros and geo_cost_micros, and credit_grants (id, user_id, kind trial | purchase | refund | adjust, micros, stripe_session_id unique and nullable, at). scripts/snapshot.sh's explicit table list keeps all of these out of data snapshots.
  2. Sign-up grant. Better Auth's databaseHooks.user.create.after inserts a trial grant of 100 × the price (195,000 µ$ at $1.95) and sets credit_micros in the same transaction.
  3. Charging a lookup. These are the tokens. In resolveAccess, after a dashboard key verifies (master keys skip this), one statement reserves the price and grows the allowance:
    UPDATE "user" SET credit_micros = credit_micros - $price, geo_allowance_micros = geo_allowance_micros + $price * 0.8 WHERE id = $1 AND credit_micros >= $price RETURNING …. No row means 402 NO_CREDITS. If the lookup is declined (422) or fails (5xx), the same amounts are reversed, so declines are free. Cached repeats are charged.
  4. Spending the allowance. A new accountBudget(userId) wraps postgresGeocodeBudget. For a provider with costPerCall > 0, reserve() first runs UPDATE "user" SET geo_allowance_micros = geo_allowance_micros - $cost WHERE id = $1 AND geo_allowance_micros >= $cost, and only then takes the vendor cap. The standardizer and Jev reserve the same way. The locator already asks providers in cost order, so a thin allowance just means it stops at the free ones. Each row's geo_cost_micros records what was spent.
  5. Dashboard. /login, and /dashboard with Home (credit and lookups left, a request example, recent lookups), API keys and History, as in artifacts/dashboard-mockup.html. Signed in, the top bar has only the wordmark. "Add credit" shows "Buying opens soon" until phase 3.

  • A repeat within 24 hours returns X-OpenTaxRate-Cache: hit and calls no geocoder.
  • The dashboard flow (sign in, create a key, curl, see it in History) works on a staging Worker in both themes.

Phase 3: buying credit with Stripe

Top-ups of $10, $25 or $50 through Stripe Checkout, credited by webhook. Credit is a prepaid balance, so there are no subscriptions, invoices or meters, and the request path never calls Stripe. The ledger in Postgres decides who can make a lookup. Stripe only takes the money.

  1. Checkout. POST /v1/account/checkout {"amount": 1000} (cents; 1000, 2500 or 5000) uses the session cookie. The first time, it creates a Stripe customer (stripe.customers.create({ email, metadata: { user_id } })) and saves stripe_customer_id. Then it calls stripe.checkout.sessions.create({ mode: "payment", customer, line_items: [{ price_data: { currency: "usd", unit_amount: amount, product_data: { name: "OpenTaxRate credit" } }, quantity: 1 }], metadata: { user_id }, success_url: "https://opentaxrate.com/dashboard?paid={CHECKOUT_SESSION_ID}", cancel_url: "https://opentaxrate.com/dashboard" }) and returns its url.
  2. Webhook. POST https://api.opentaxrate.com/api/billing/webhook comes straight from Stripe through Caddy, not the Worker, so the raw body reaches stripe.webhooks.constructEvent(raw, signature, STRIPE_WEBHOOK_SECRET) untouched. On checkout.session.completed with payment_status === "paid", one transaction runs INSERT credit_grants (kind 'purchase', micros = amount_total × 10,000, stripe_session_id) ON CONFLICT (stripe_session_id) DO NOTHING, and only if a row went in, adds the same to credit_micros. A replayed event changes nothing. charge.refunded inserts a negative refund grant.
  3. Dashboard. Home's "Add credit" offers $10, $25 and $50, showing about 5,128, 12,820 and 25,641 lookups at $1.95. ?paid= shows "Credit added" once the webhook lands; it polls /v1/account/summary for up to 10 s. /pricing's button becomes "Get a key".

Open questions

  1. Should the public tier keep Census? Recommended: no, as you asked, but decide after the phase 1 bench. Census is free, needs no key, and is the only TIGER dataset, so it's the one provider that gives Photon and Pelias an independent second opinion. If public refusals rise sharply without it, adding census to the public list is a one-line change. The public Nominatim stays out either way, because its usage policy allows one request a second.
  2. What about outside calls that aren't geocoders? These are the Census ZCTA check in insideTypedZip and California's CDTFA lookup. Recommended: keep them public. They're free government checks that a lookup's correctness depends on, not providers you pay for.
  3. Which mail sender? Recommended: Resend, one HTTP call from src/mail.ts with a verified opentaxrate.com domain. Cloudflare's email sending is the alternative if you'd rather keep everything in one account.
  4. Which key header? Recommended: accept both x-api-key (Better Auth's default) and Authorization: Bearer. Most HTTP clients make one or the other easy.
  5. Should the landing page use keyed lookups for a signed-in user? Recommended: not now. Keys are for servers. The browser stays public, so the demo shows exactly what an anonymous caller gets.
  6. Open sign-up or a waitlist? Recommended: open. Better Auth's own limit on code sends (by X-Client-IP) plus the Worker's AUTH limit cover abuse. Add Turnstile to /login only if you see it.
  7. Should credit expire? Recommended: no. Unused credit costs nothing to hold, and expiry is the kind of fine print the pricing table is meant to avoid.
  8. Should the vendors behind the key stay unnamed? Recommended: yes on the site. /pricing says "commercial geocoders". The API still names them in /v1/coverage and in trace.geocoders[].source. Hiding those means mapping provider ids to neutral labels in geocoderCoverage() and the trace before responding.
  9. Should a repeat answered from history be charged? Recommended: yes, at the same $0.00195. It's simplest to explain, and the margin pays for the misses. cached is on every row if you later want hits to be free.

Appendix: words and concepts this page assumes

Tier and policy

A tier is what a request may use, and a policy is that tier turned into the set of provider ids the registry may return.

OPENTAXRATE_PUBLIC_PROVIDERS=photon,pelias
policyFor({ tier: "public" }).allows("mapbox")  // false
policyFor({ tier: "keyed" }).allows("mapbox")   // true
unset variable → every id allowed (self-host default)

Email OTP

A one-time code sent by email. Typing it proves you own the address, so sign-in and verification are the same step.

emailOTP({ otpLength: 6, expiresIn: 300, allowedAttempts: 3,
  storeOTP: "hashed",
  sendVerificationOTP: ({ email, otp }) => sendMail(email, otp) })

Better Auth API key

A random secret whose hash is stored. Verifying it looks up the hash, checks that it's enabled and not expired, and applies the per-key rate limit. Spending is checked separately, against the account's credit.

await auth.api.verifyApiKey({ body: { key } })
→ { valid: true, key: { id: "key_71b0", userId: "usr_9f2c",
    rateLimitMax: 120, metadata: {} } }

Independent dataset

The locator counts agreement between datasets, not providers. Two OSM-backed geocoders that agree count as one vote.

photon  → osm            ┐ one dataset → single-dataset path
pelias  → osm            ┘ (accept only inside Austin's outline)
census  → tiger          ┐ two datasets → agreement within
nominatim → osm          ┘ the coarser margin and 250 m

Same-origin auth through the Worker

The dashboard and /api/auth are both on opentaxrate.com, so the session cookie is first-party and needs no CORS credentials.

opentaxrate.com/api/auth/sign-in/email-otp
  → Worker → API (VPC binding) /api/auth/…
  ← Set-Cookie: better-auth.session_token=…; HttpOnly; Secure; SameSite=Lax

Vendor cap

The existing per-credential daily cap and spacing in geocoder_usage, reserved with one upsert before every call. It's shared by both tiers.

MAPBOX_DAILY_CAP=300 → the 301st Mapbox call today is skipped,
whichever key or tier asked
