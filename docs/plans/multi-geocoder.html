Design plan · proposed · branch animated-jaguar · 2026-10-21

Many geocoders, asked only when the answer needs them

Today every map lookup asks Mapbox, the Census Bureau and Nominatim at the same time, so adding a provider adds a call to every lookup. This plan turns each geocoder into a provider that is switched on by its API key. A lookup asks two of them, cheapest first. A precise (and usually paid) geocoder is asked only when the engine finds a city or district line that would change the rate and that a sharper point could settle. Results are cached in Postgres where the provider's terms allow it, and each provider gets a rate limit, a daily cap and a circuit breaker.

Why change how addresses are placed

The map engine covers 16 states: TX, FL, NY, PA, IL, VA, AZ, NM, CO, AK, AL, LA, SC, MS, ID and HI. Its rate is only as good as the point the address is placed at. The range engine also needs a point when a ZIP is split between rates. Today locateAddress() sends every configured geocoder the address at once, keeps the most precise point, and gives up when the points are more than 250 m apart. That was fine with three free or cheap geocoders. It does not scale to ten:

  • Every lookup pays for every provider. A Google or HERE key would be called for an address in the middle of Austin that the free Census point already settles.
  • Nominatim's queue slows everything down. The public server allows one request a second. The spacing lives in a variable in one process (nominatimFree), so lookups queue behind it, and several API containers would each send one a second.
  • Nothing is remembered. Repeat customers' addresses are geocoded again on every order.
  • Geocoders that read the same data count as two votes. Pelias and Nominatim both read OpenStreetMap, so their agreeing proves less than Census and OpenStreetMap agreeing.

The decision: a geocoding module outside the engine holds a registry of providers. It answers the engine's request "place this address" by asking two providers that use different data. It answers the follow-up "place it with a margin under d metres" by asking only providers precise enough to settle that. The engine keeps deciding which lines matter; the geocoding module decides who to ask. Out of scope: self-hosting Pelias or Nominatim (the registry only takes a URL), batch geocoding during refresh, and showing the point to callers.

A more precise point means a smaller margin

A geocoded point is the true location give or take some error. If a city line is closer than that error, the house could be on either side. EDGE_METRES in src/engine/types.ts sets the margin by how the geocoder placed the address:

AccuracyMarginHow it's placedWhat providers call it
rooftop15 mon the buildingGoogle ROOFTOP, Geocodio rooftop, Smarty Rooftop, Mapbox rooftop
parcel25 mthe middle of the lotSmarty Parcel, Mapbox parcel
point40 man address point, such as one from OSMNominatim with a house number, Pelias point, HERE houseNumberType: PA, Geocodio point
interpolated75 mestimated along the street's range of house numbersCensus, Google RANGE_INTERPOLATED, Geocodio range_interpolation, HERE interpolated

If an outline's edge falls inside the margin, the engine also prices a point 2 m across the line, and refuses only if the rate there differs. A smaller margin puts fewer addresses near any edge, so there are fewer refusals. These margins are the code's own assumptions, not vendor guarantees, and "rooftop" means different things at different vendors. The lon,lat columns in the bench cases (artifacts/bench/cases) give true points, so phase 4 measures each provider's distance from them and sets its margin from that.

  • Each provider maps its own labels, cautiously. A label it doesn't recognise, or a centroid such as Google GEOMETRIC_CENTER or Smarty Zip9, is not a point and the provider returns nothing.

What changes from the proposal

Most of the proposal stays: providers switched on by API key, at least two sources, rooftop calls only near lines, an order by tier and cost, a limiter and breaker per provider, and a storable flag. Four parts change, each to spend fewer calls or refuse fewer good addresses.

  1. Escalate on a deciding line, not on any line within 75 m. Many lines near a point don't change the rate: county lines between counties with no sales tax, district seams, and city lines where a Texas combined area keeps the same total. geoRateAt() already works out the rate 2 m across each nearby edge. It escalates only when that rate differs, and it passes the distance d to the nearest such edge.
  2. Ask only providers that can settle it. locate({ marginUnder: d }) asks only providers whose accuracy has a margin under d. For an edge 31 m away that means parcel (25 m) or rooftop (15 m). For an edge 10 m away nothing can settle it, so no call is spent and the address is refused at once.
  3. The engine asks; it does not hand over a predicate. The proposal had the locator take an escalate callback that would need the engine's edges. Instead the engine calls the same lazy locate callback a second time with the margin it needs. Each module keeps its own knowledge, and the callback stays one function.
  4. Count data sources, not providers. Each point carries its data source, such as tiger, osm, openaddresses, here or google. Pelias and Geocodio report a source for each result, so it is set per point, not per provider. Two points agree only if they come from different sources. With three or more points, the largest group that agrees wins, so one outlier no longer sinks an address the others agree on.

The proposal's step "escalate when the point is within 75 m of a line" goes away, because 75 m was just the coarsest margin. Its step "escalate when one fails" stays, as "ask the next provider when fewer than two sources have placed it".

Rules

  • Two different data sources, or a checked single. A point is used when two points from different sources fall within the coarser one's margin of each other. A point from one source alone is used only if it lies inside the typed city's outline (see open question 1).
  • The engine decides when a sharper point is worth buying. The locator never escalates by itself after stage 1. It asks stage 2 providers only when locate({ marginUnder }) is called, and then only providers whose EDGE_METRES is below that number.
  • At most one sharpening per lookup. The engine calls locate at most twice. A sharper point that still leaves a deciding line within its margin is refused as today, naming both rates.
  • A sharper point must agree with the pair. It's used only if it lies within the pair's margin, so a precise wrong match cannot override two coarse right ones.
  • Only storable results are cached. A provider marked storable: false is remembered for the request and then dropped. "No match" answers are cached for 30 days so a bad address isn't asked about again on every order; points are cached for a year.
  • Caps are never exceeded. A call takes a slot from geocoder_usage before it's sent. A provider at its cap, out of tokens, or with an open breaker is skipped, never queued.
  • Missing data is never a point. Timeouts, errors and skipped providers count as "didn't place it", and they're logged on the lookup so a refusal can say "Census and OpenStreetMap disagree; no third geocoder was available".

Open questions

  1. Should one geocoder alone ever be enough? Requiring two would refuse addresses that OpenStreetMap has no house number for, and US house-number coverage in OSM is patchy. Recommended: accept one point when no second source is available, but only if it falls inside the outline of the city the customer typed (or the county of the typed ZIP). That catches the "same street in the next town" error that a margin can't. Measure the refusal and error rates on the bench before and after.
  2. Is the API allowed to write? docs/architecture.md says the API never writes. Recommended: allow writes to the two geocoding tables only, which refresh never reads, and add OPENTAXRATE_GEOCODE_CACHE=off for read-only deployments.
  3. Should Google be offered at all? Its terms limit storing results and using them away from a Google map. Recommended: ship the provider, mark it storable: false, and note the terms in the README, so the person running it decides with their own key.
  4. Should the per-second limit be shared across containers? Recommended: no. Keep the token bucket in memory and divide the rate by OPENTAXRATE_API_REPLICAS. The daily cap, the limit that costs money, is shared through Postgres.
  5. Should the answer say which geocoders placed it? Recommended: yes, in source, e.g. "placed by Census and OpenStreetMap, then Geocodio rooftop". It costs nothing and helps when someone disputes a rate.

Appendix: words and concepts this page assumes

Margin

How close to a line a point may be before it could be on either side. A deciding edge closer than the margin means the engine can't tell which rate applies.

marginOf(p) = p.metres ?? EDGE_METRES[p.accuracy]
rooftop 15 · parcel 25 · point 40 · interpolated 75

Deciding edge

An outline edge within the margin where the rate 2 m across differs from the rate at the point. Edges with the same rate on both sides are ignored.

edge 31 m, rate here 8.25%, rate across differs → deciding
edge 12 m, rate across 8.25% → ignored

Data source

Where a point's data came from, independent of who served it. Agreement counts only between different sources.

census → tiger · nominatim → osm
pelias → osm | openaddresses (per result)
nominatim + pelias(osm) = one source

Token bucket

A rate limiter: a provider's bucket refills at its allowed rate, and a call needs a token. With no token left the provider is skipped for this lookup.

nominatim: 1 token/s, size 1
t=0.0 call ok · t=0.4 skipped · t=1.0 call ok

Circuit breaker

After repeated failures a provider is skipped for a while instead of being waited on, then tried once to see if it has recovered.

5 errors or one 429 → open for 60 s
then one trial call: ok → closed, fail → open again

Daily cap slot

One atomic update both counts the call and refuses it at the cap, so several containers share one budget.

INSERT INTO geocoder_usage (provider, day, calls)
VALUES ('geocodio', current_date, 1)
ON CONFLICT (provider, day) DO UPDATE
  SET calls = geocoder_usage.calls + 1
  WHERE geocoder_usage.calls < 2500
RETURNING calls;   -- no row → at cap, skip
