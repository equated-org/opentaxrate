OpenTaxRate · Operations

Self-hosted geocoders

How to run Nominatim, Photon and Pelias for the US on one machine, connect OpenTaxRate to them, and keep their data current.

Written 2026-10-22 from the geocoder.example.test install · Geocoding design · README

OpenTaxRate places an address on the map only when the states’ street and ZIP files can’t settle a rate. It can ask public services, but the public Nominatim allows one request a second and the vendors bill per call. Running your own removes both limits.

Three geocoders

ServiceDataPortBuilt on the host?How it stays current
Nominatim 5.3OpenStreetMap, Census TIGER house-number ranges, US ZIP centroids8080Yes, about 6 hUpdates itself from OpenStreetMap’s daily changes; TIGER once a year
Photon 1.3OpenStreetMap, exported from a Nominatim database2322No, a 14 GB prebuilt downloadSwap in GraphHopper’s newer build when one appears
PeliasOpenStreetMap, OpenAddresses, Who’s On First, TIGER interpolation4000Yes, about 3 h plus interpolationFull rebuild every few months

The Census Bureau’s geocoder has no self-hosted edition; OpenTaxRate keeps calling it directly.

Point OpenTaxRate at them

NOMINATIM_URL=http://geocoder.example.test:8080
PHOTON_URL=http://geocoder.example.test:2322
PELIAS_URL=http://geocoder.example.test:4000

NOMINATIM_URL replaces the public server and raises its spacing from one request a second to ten. Photon and Pelias are only called when their URL is set. All three default to 10 requests a second and 100,000 a day; <NAME>_RATE_PER_SECOND and <NAME>_DAILY_CAP override them (NOMINATIM_, PHOTON_, PELIAS_). Changing a URL changes the cache fingerprint, so results cached from the public server aren’t reused for yours.

Check each one:

curl -s 'http://geocoder.example.test:8080/status?format=json'
curl -s 'http://geocoder.example.test:8080/search?q=1600+Pennsylvania+Ave+NW,+Washington+DC&format=jsonv2&limit=1'
curl -s 'http://geocoder.example.test:2322/status'
curl -s 'http://geocoder.example.test:2322/api?q=1600+Pennsylvania+Ave+Washington&limit=1'
curl -s 'http://geocoder.example.test:4000/v1/search?text=1600+Pennsylvania+Ave+NW,+Washington+DC&size=1'

The machine

The examples support an ARM64 host. Size CPU, memory and storage for the datasets you import.

ServiceDiskRAM while serving
Nominatim (Postgres + flatnode)About 400–500 GB10–30 GB, mostly page cache
Pelias (Elasticsearch + source files)About 200 GB index + 150 GB sourcesAbout 25 GB
Photon14 GB2–6 GB (8 GB heap cap)

Ensure enough free memory for imports and avoid competing memory-intensive workloads.

Nominatim

First install

mkdir -p ~/nominatim/pgdata ~/nominatim/flatnode
docker run -d --name nominatim --restart unless-stopped --shm-size=4g \
  -e PBF_URL=https://download.geofabrik.de/north-america/us-latest.osm.pbf \
  -e REPLICATION_URL=https://download.geofabrik.de/north-america/us-updates/ \
  -e UPDATE_MODE=continuous \
  -e IMPORT_US_POSTCODES=true \
  -e IMPORT_TIGER_ADDRESSES=true \
  -e IMPORT_WIKIPEDIA=true \
  -e THREADS=18 \
  -e POSTGRES_SHARED_BUFFERS=8GB -e POSTGRES_MAINTENANCE_WORK_MEM=16GB \
  -e POSTGRES_AUTOVACUUM_WORK_MEM=2GB -e POSTGRES_WORK_MEM=128MB \
  -e POSTGRES_EFFECTIVE_CACHE_SIZE=64GB -e POSTGRES_MAX_WAL_SIZE=8GB \
  -e POSTGRES_CHECKPOINT_TIMEOUT=30min \
  -v $HOME/nominatim/pgdata:/var/lib/postgresql/16/main \
  -v $HOME/nominatim/flatnode:/nominatim/flatnode \
  -p 8080:8080 mediagis/nominatim:5.3
docker logs -f nominatim

The API answers once the log says Import completed successfully. On geocoder.example.test the 2026-10-21 import took 5 h 50 min: download 20 min, osm2pgsql 32 min, streets 84 min, house numbers and points of interest 2 h 20 min, search indexes 12 min.

Three of those flags matter most:

  • IMPORT_TIGER_ADDRESSES=true adds the Census house-number ranges for every US street segment. Without them Nominatim knows only the house numbers mapped in OpenStreetMap, which most of the US lacks.
  • UPDATE_MODE=continuous keeps the data current: the container applies Geofabrik’s daily US changes itself (see Keeping it current).
  • IMPORT_WIKIPEDIA=true loads place importance. Without it “350 5th Ave, New York, NY” resolves to Smithtown, Long Island, because nothing ranks Manhattan above it.

The geocoder.example.test import ran without TIGER, Wikipedia importance or continuous updates. TIGER 2025 was added and the container recreated with UPDATE_MODE=continuous and IMPORT_TIGER_ADDRESSES=true on 2026-10-22. Wikipedia importance is still missing (below).

Adding TIGER to an existing database

Nominatim publishes the Census TIGER address ranges preprocessed. nominatim.org returns 403 without a User-Agent.

docker exec nominatim bash -c 'cd /nominatim &&
  curl -sSL -A "opentaxrate-setup" -o tiger.csv.tar.gz \
    https://nominatim.org/data/tiger2025-nominatim-preprocessed.csv.tar.gz &&
  chown nominatim tiger.csv.tar.gz &&
  sudo -E -u nominatim nominatim add-data --tiger-data /nominatim/tiger.csv.tar.gz --threads 16'
docker exec nominatim bash -c 'grep -q USE_US_TIGER /nominatim/.env ||
  echo NOMINATIM_USE_US_TIGER_DATA=yes >> /nominatim/.env'
docker exec nominatim bash -c 'cd /nominatim && sudo -E -u nominatim nominatim refresh --functions'
docker restart nominatim

The API keeps serving during add-data. .env lives in the container, not on a volume: if you ever recreate the container, pass -e IMPORT_TIGER_ADDRESSES=true so the start script writes that line again. It won’t re-import anything; the import only runs when pgdata is empty.

A new TIGER release appears each autumn as tigerYYYY-nominatim-preprocessed.csv.tar.gz; load it the same way, and it replaces the old ranges. List them with curl -sA x https://nominatim.org/data/ | grep -o 'tiger[0-9]*-nominatim[^"]*' | sort -u. Delete the downloaded file afterwards (docker exec nominatim rm /nominatim/tiger.csv.tar.gz).

Adding Wikipedia importance to an existing database

docker exec nominatim bash -c 'cd /nominatim &&
  curl -sSL -A "opentaxrate-setup" -o wikimedia-importance.csv.gz \
    https://nominatim.org/data/wikimedia-importance.csv.gz &&
  chown nominatim wikimedia-importance.csv.gz &&
  sudo -E -u nominatim nominatim refresh --wiki-data --importance'

This recomputes importance for every place, which takes about an hour; searches keep working. Refresh it yearly.

Keeping it current

With UPDATE_MODE=continuous the container checks Geofabrik every 15 minutes and applies each day’s US changes as they appear, usually in a few minutes. Nothing else is needed. /status?format=json reports data_updated; Geofabrik publishes about a day behind, so up to two days old is normal.

curl -s 'http://geocoder.example.test:8080/status?format=json'
docker exec nominatim tail -5 /var/log/replication.log   # "No new changes. Sleeping for 900 sec." when current

Each container start re-reads the data’s date and re-applies the latest day of changes, which is harmless. If the updater stops, the container keeps serving the old data; a restart (docker restart nominatim) starts it again.

To turn continuous updates on for an existing database, recreate the container with the same volumes and the flags above; the import doesn’t run again because pgdata already holds the data.

docker stop nominatim && docker rm nominatim
docker run -d --name nominatim … -e UPDATE_MODE=continuous -e IMPORT_TIGER_ADDRESSES=true …   # same command as First install

Photon

Install from the prebuilt US dump

GraphHopper publishes a US Photon database built from their own Nominatim import, weekly. Downloading it is far quicker than building one.

mkdir -p ~/photon && cd ~/photon
curl -sSLO https://github.com/komoot/photon/releases/download/1.3.0/photon-1.3.0.jar
docker run --rm -v ~/photon:/w -w /w debian:stable-slim sh -c '
  apt-get update -qq && apt-get install -y -qq curl lbzip2 ca-certificates >/dev/null &&
  curl -sSL https://download1.graphhopper.com/public/north-america/usa/photon-db-usa-1.0-latest.tar.bz2 |
  lbzip2 -d | tar x && chown -R 1000:1000 /w'
docker run -d --name photon --restart unless-stopped -p 2322:2322 \
  -v ~/photon:/photon -w /photon eclipse-temurin:21-jre \
  java -Xmx8g -jar photon-1.3.0.jar serve -data-dir /photon -listen-ip 0.0.0.0

Keeping it current

GraphHopper rebuilds the US dump every few days. A newer one is available when the dump’s Last-Modified is later than Photon’s import_date:

curl -sI https://download1.graphhopper.com/public/north-america/usa/photon-db-usa-1.0-latest.tar.bz2 | grep -i last-modified
curl -s http://localhost:2322/status

To swap it in, unpack it beside the live database (about 20 minutes), then swap with Photon stopped (about a minute of downtime) and keep the old database until the new one works:

cd ~/photon && rm -rf next && mkdir next
docker run --rm -v ~/photon/next:/w -w /w debian:stable-slim sh -c '
  apt-get update -qq && apt-get install -y -qq curl lbzip2 ca-certificates >/dev/null &&
  curl -sSL https://download1.graphhopper.com/public/north-america/usa/photon-db-usa-1.0-latest.tar.bz2 |
  lbzip2 -d | tar x && chown -R 1000:1000 /w'
docker stop photon && mv photon_data photon_data.prev && mv next/photon_data photon_data && docker start photon
curl -s 'http://localhost:2322/api?q=1600+Pennsylvania+Ave+Washington&limit=1'   # must return a Feature
rm -rf photon_data.prev next
# if the search fails instead: docker stop photon; rm -rf photon_data; mv photon_data.prev photon_data; docker start photon

Alternatively, build Photon from your own Nominatim, so both share one dataset (including TIGER) and Photon follows Nominatim’s changes. This needs Nominatim’s Postgres port reachable from the Photon container; the mediagis image doesn’t publish 5432, so add -p 127.0.0.1:5432:5432.

# once: export Nominatim into a fresh Photon database
java -jar photon-1.3.0.jar import -host 127.0.0.1 -database nominatim -user nominatim \
  -password '<password>' -country-codes us -languages en -data-dir /photon/new -j 16
java -jar photon-1.3.0.jar update-init -host 127.0.0.1 -user nominatim -password '<password>'
# after each Nominatim replication run
java -jar photon-1.3.0.jar update -host 127.0.0.1 -user nominatim -password '<password>' -data-dir /photon

geocoder.example.test still runs the prebuilt dump; building from your own Nominatim hasn’t been tried there.

Pelias

Pelias is driven by the pelias/docker CLI. On geocoder.example.test the CLI is ~/pelias/src/pelias, the project (docker-compose.yml, pelias.json, .env) is ~/pelias/project, and data is ~/pelias/data. ~/pelias/stage.sh NAME cmd… runs a step with its log in ~/pelias/logs/NAME.log and timings in ~/pelias/logs/timing.log.

Build

Run from ~/pelias/project. Times are from the 2026-10-21 geocoder.example.test build.

P=~/pelias/src/pelias; S=~/pelias/stage.sh
$P compose pull
$P elastic start && $P elastic wait && $P elastic create
$S download_wof   $P download wof              #  2 min
$S download_tiger $P download tiger            # 25 min, 3,221 county files
bash ~/pelias/dl_osm.sh                        # 16 min, Geofabrik us-latest.osm.pbf
bash ~/pelias/dl_oa.sh && bash ~/pelias/extract_oa.sh   # OpenAddresses, see below
bash ~/pelias/polylines_big.sh                 # 49 min, see below
$S prepare_placeholder $P prepare placeholder  #  1.5 min
$P compose up -d libpostal placeholder pip
$S import_wof $P import wof                    #  0.5 min
$S import_osm $P import osm                    #  2 h
$S import_oa_p1 docker compose run --rm openaddresses ./bin/parallel 6 /data/openaddresses/p1   # 53 min
$S import_oa_p2 docker compose run --rm openaddresses ./bin/parallel 6 /data/openaddresses/p2   # 98 min
$S build_interpolation docker compose run --rm interpolation bash ./docker_build.sh             # several hours
$P compose up -d api interpolation

The OpenStreetMap and OpenAddresses imports can run at the same time. The API can start as soon as the Elasticsearch index exists; it serves whatever has been imported so far, and uses interpolation once that service is up.

Three steps don’t work as shipped for the whole US:

  • OpenAddresses. pelias download oa no longer finds the US files. dl_oa.sh fetches the four regional collections from https://v2.openaddresses.io/batch-prod/collection-us-{west,south,midwest,northeast}.zip, and extract_oa.sh unpacks only the *-addresses-*.geojson files, putting priority states in p1 and the rest in p2 so the important states are searchable first.
  • Polylines. pelias prepare polylines refuses a PBF this large (“The file is too large”). polylines_big.sh runs the same pbf streets extractor directly with a 70 GB memory limit, writing /data/polylines/extract.0sv.
  • Interpolation from OpenAddresses. The interpolation builder reads only *.csv, and OpenAddresses now ships GeoJSON, so its OpenAddresses step adds nothing; house-number ranges come from TIGER and OpenStreetMap. Converting the GeoJSON to OpenAddresses CSV (LON,LAT,NUMBER,STREET,UNIT,CITY,DISTRICT,REGION,POSTCODE,ID,HASH) under /data/openaddresses before the build would add them.

Keeping it current

Pelias has no incremental updates. Rebuild it from fresh downloads every three months, into a second index beside the live one so searches keep working, then switch over. A rebuild takes most of a day and needs about 150 GB free for the second index. Run from ~/pelias/project:

D=~/pelias/data; NEXT=pelias_$(date -u +%Y%m%d)
LIVE=$(jq -r '.schema.indexName // "pelias"' pelias.json)
jq --arg i $NEXT '.schema.indexName = $i' pelias.json > pelias.next.json
# run an importer against the new index
next() { docker compose run --rm -T -v $PWD/pelias.next.json:/code/pelias.next.json:ro -e PELIAS_CONFIG=/code/pelias.next.json "$@"; }

# 1. fresh downloads (about 1 h)
docker compose run --rm -T whosonfirst ./bin/download
docker compose run --rm -T interpolation ./bin/download-tiger
bash ~/pelias/dl_osm.sh
rm -rf $D/openaddresses.next && mkdir $D/openaddresses.next
for c in us-west us-south us-midwest us-northeast; do
  curl -sSLf -o $D/raw/oa/collection-$c.zip https://v2.openaddresses.io/batch-prod/collection-$c.zip
  unzip -o -qq $D/raw/oa/collection-$c.zip 'us/*-addresses-*.geojson' -x '*.meta' -d $D/openaddresses.next
done
rm -rf $D/openaddresses && mv $D/openaddresses.next $D/openaddresses
bash ~/pelias/polylines_big.sh

# 2. admin areas (placeholder is down for a few minutes)
docker compose stop placeholder && ~/pelias/src/pelias prepare placeholder
docker compose up -d placeholder pip libpostal

# 3. import into the new index (about 4 h; OSM and OpenAddresses can run together)
next schema ./bin/create_index
next whosonfirst ./bin/start
next openstreetmap ./bin/start
next openaddresses ./bin/parallel 6 /data/openaddresses
next polylines ./bin/start

# 4. interpolation into a new directory (several hours)
docker compose run --rm -T -e BUILDDIR=/data/interpolation.next interpolation bash ./docker_build.sh

# 5. switch over, only if the new index has over 100 million documents
curl -s localhost:9200/_cat/count/$NEXT
cp pelias.json pelias.json.prev && cp pelias.next.json pelias.json
docker compose stop interpolation
mv $D/interpolation $D/interpolation.prev && mv $D/interpolation.next $D/interpolation
docker compose up -d --force-recreate api interpolation
curl -s 'localhost:4000/v1/search?text=1600+Pennsylvania+Ave+NW,+Washington+DC&size=1'   # must return a Feature
curl -XDELETE localhost:9200/$LIVE && rm -rf $D/interpolation.prev pelias.json.prev pelias.next.json
# if the search fails instead: restore pelias.json.prev and interpolation.prev, recreate api and interpolation

Rebuilding into the live index instead would mix old and new data until it finished, and deleted places would linger.

This rebuild hasn’t been run end to end on geocoder.example.test; the first build used the separate steps under Build.

Automatic updates

Nominatim updates itself (above). Everything else runs from a prompt: once a week, cron starts Claude Code on geocoder.example.test with deploy/geocoders/maintain.md, which follows this guide to:

  • check each geocoder answers a test search, Nominatim’s data is under 3 days old, interpolation is running and disk is not low;
  • swap in a newer Photon build;
  • load a new TIGER release into Nominatim, October to December;
  • rebuild Pelias when its index is over 3 months old, one long step per run, recording progress in ~/geocoders/notes.md;
  • append a report of what it found and did to ~/geocoders/logs/maintain.log.

Install

The prompt reads this guide, so copy both to geocoder.example.test (again whenever either changes), then add the cron line:

scp deploy/geocoders/maintain.md docs/self-hosted-geocoders.html geocoder.example.test:geocoders/
ssh geocoder.example.test crontab -e
0 6 * * 1 cd ~/geocoders && { date -u; ~/.local/bin/claude -p "$(cat maintain.md)" --dangerously-skip-permissions; } >> logs/maintain.log 2>&1

That runs every Monday at 06:00 UTC. Claude Code must be logged in on geocoder.example.test: run claude there once and use /login. To run it now, paste the same command into a shell. To see what it did, tail -50 ~/geocoders/logs/maintain.log.

The run makes changes without asking, so it uses --dangerously-skip-permissions; the prompt limits it to the geocoders, one change per run, and deleting only what this guide says to delete. After a Pelias rebuild or a new TIGER release, rerun the geocoder benchmark (tsx scripts/bench.ts geocode) to confirm nothing regressed.

Troubleshooting

  • Nominatim API down during import. Normal: the web server starts only after Import completed successfully. Progress: docker logs --tail 5 nominatim.
  • Control server error: Permission denied: '/root/.gunicorn' in the Nominatim log is harmless; the API works.
  • du shows ~/nominatim/pgdata as 4 KB. The directory belongs to the container’s Postgres user. Use docker exec nominatim du -sh /var/lib/postgresql/16/main.
  • Downloads from nominatim.org return 403. Send a User-Agent (curl -A …).
  • The weekly run did nothing. Check ~/geocoders/logs/maintain.log; “Not logged in” means Claude Code on geocoder.example.test needs /login.
  • Pelias returns results without house-number interpolation. The interpolation service isn’t running or its build is unfinished: docker ps | grep interpolation, tail ~/pelias/logs/build_interpolation.log.
