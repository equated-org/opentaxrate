OpenTaxRate · Internal planning

Jurisdiction resolution: lessons from Stripe

Keep the hybrid lookup engines and PostGIS. Improve historical boundaries, source validation and uncertainty handling before adding a new spatial service.

Architecture review · Version 1 · 2026-10-22 · Proposed work

Assessment

OpenTaxRate already uses PostGIS. The biggest opportunity is improving how jurisdiction boundaries are validated, versioned and resolved, rather than changing databases. Keep the hybrid engines and evolve the spatial data model.

This review examined architecture notes, the schema, map lookup, geometry processing and supplemental polygon verification. It did not measure production accuracy or latency. Recommendations below are proposed work, not implemented capabilities.

Stripe precomputes nonoverlapping regions representing combinations of taxing jurisdictions, retains historical versions, and uses a spatial index to narrow candidates before exact containment checks. It also splits disconnected regions to improve indexing. The useful lessons are preparing data offline and treating boundaries as historical data. The article does not establish comparative accuracy or explain enough of its geocoding and uncertainty handling to judge those against OpenTaxRate. Stripe’s architecture article.

What is working well

The hybrid architecture uses the evidence each state actually provides. An official street-to-tax-area assignment contains information that ordinary postal city and ZIP matching does not. Replacing it with geocoding everywhere could introduce uncertainty and cost.

There is already a foundation for precomputed tax regions: sales_tax_areas represents jurisdiction combinations, and supplemental verification attaches polygons to verified combinations. Build on the existing verification pipeline.

Version historical boundaries consistently

This is the clearest architectural gap found. Rate rows have effective dates. Shapes also have date fields used by the supplemental indexed-area path. However, general map helpers shapesAround() and shapesHolding() accept no lookup date. Ordinary shapes are unique by state, kind and FIPS identifier, and loaders replace geometry.

Dated rates alone therefore do not guarantee historically correct map results. An annexed address can require the old city boundary as well as the old rate. Introduce immutable boundary editions with effective intervals, source snapshot IDs and stable jurisdiction identities. Each lookup should select a coherent edition for its requested date. Preserve acquisition time separately from legal effective time, and refuse unsupported historical dates.

Benefit: defensible historical answers and reproducible investigations. Cost: storage, migration work and sourcing historical boundaries that schema changes cannot manufacture.

Implementation evidence

Shape schema; map queries; dated supplemental lookup; loaders.

Validate relationships between boundaries

The loader repairs and dissolves shapes, then simplifies them at roughly metre scale. This helps individual shapes, but ST_SimplifyPreserveTopology does not preserve shared boundaries between separate polygons. PostGIS documents this limitation.

  • Coverage checks. Detect unexpected gaps and overlaps within layers intended to partition an area.
  • Change checks. Detect missing features, unexplained coverage changes, boundary movement and affected benchmark addresses.
  • Binding checks. Detect conflicting tax-area assignments and missing rate bindings.

City and district overlaps can be legitimate. Use source-specific rules; automatically snapping every layer into a gapless map could invent tax boundaries. Preserve original geometry separately from derived lookup geometry. Quantify simplification displacement and include it in uncertainty.

Benefit: catches source and transformation problems before publication. Cost: some findings require research rather than automatic repair. See geometry processing.

Strengthen the meaning of one answer

The map engine samples points two metres across nearby boundaries and compares total rates. A nearest-edge sample does not establish every possible jurisdiction combination around complicated intersections, narrow districts or several nearby boundaries. Consider every tax region intersecting the location’s uncertainty footprint, then compare the possible outcomes. Precomputed regions would make this easier.

Distinguish rate certainty from jurisdiction certainty. Two regions can have the same total but different collecting jurisdictions. The current comparison uses other.rate !== answer.rate, while responses also include jurisdiction parts and a location code. A common rate can be useful for a rate-only consumer even when the breakdown remains uncertain. Represent that distinction explicitly or require agreement on jurisdiction identity.

Benefit: stronger boundary handling and response semantics. Cost: potentially more refusals and spatial work. Calibrate the uncertainty footprint as well. See map lookup and edge checks.

Pilot precomputed tax regions

Build a derived region layer over existing sources and levy rules, starting with one map state with strong authoritative boundaries and benchmark evidence. Keep street ranges and address-specific exceptions. A region identifies a jurisdiction combination, not merely a percentage; equal totals must not erase different jurisdiction identities.

Benefits: simpler runtime stacking, better overlap diagnostics and easier uncertainty checks. Costs: expensive overlay builds, small sliver polygons, historical storage and regeneration when boundaries or bindings change. Precomputation can make bad data consistently wrong. Run both engines against the same trusted cases before changing dispatch.

Improve indexing when measurements justify it

GiST indexes and indexed predicates are already present. PostGIS implements R-tree indexing through GiST, so broad spatial candidate filtering is already available. PostGIS indexing documentation.

Experiment with a separate lookup-pieces table: split disconnected multipolygons into components, subdivide complex components with ST_Subdivide, and index the pieces while retaining their parent jurisdiction or region IDs. PostGIS documents improved candidate filtering and spatial checks for subdivided datasets. ST_Subdivide documentation.

Keep boundary distances tied to real jurisdiction boundaries. Artificial subdivision seams must never become tax boundaries. Benchmark first: faster containment does not improve source accuracy, and if geocoding dominates latency, spatial optimization may barely affect the user experience.

Recommended sequence and success criteria

  1. Expand the existing benchmark. Add independently verified boundary, annexation and historical cases. Track wrong accepted answers separately from refusals, and assess jurisdiction identity as well as totals.
  2. Make boundary versions date-aware. Require coherent release selection and correct before/after answers for known boundary changes.
  3. Validate geometry changes and coverage. Detect missing districts, unexpected overlaps and transformation drift before release.
  4. Separate rate and jurisdiction certainty. Never present a definitive breakdown when only the total is settled.
  5. Pilot regions in one state. Require agreement with trusted evidence and demonstrate stronger uncertainty handling.
  6. Optimize indexing as measured. Seek better database p95/p99 latency with unchanged answers before considering a custom spatial service.

Extend the existing benchmark infrastructure. Keep the hybrid engines and PostGIS; invest first in historical boundaries, source validation and measurable uncertainty. Precomputed regions are a promising next layer, while a custom R-tree service should wait for evidence that PostGIS is the bottleneck.

Appendix: terms

PostGIS and GiST

PostGIS adds spatial operations to PostgreSQL. GiST is the index framework used here to narrow spatial candidates before exact checks.

spatial index → candidate shapes → ST_Covers

Effective and acquisition dates

Effective time says when a boundary applies. Acquisition time says when the system obtained its evidence.

requested date → applicable boundary edition
observed_at → evidence acquisition time

Uncertainty footprint

The area in which an address might plausibly lie, given geocoder and boundary limitations. It is an operational model, not proof.

footprint intersects regions A and B
compare both jurisdiction sets and totals

p95 and p99 latency

Request-duration percentiles used to measure slower requests, rather than only averages.

p95: 95% of measured durations at or below it
