OpenTaxRate · Design notes

Map engine

For states whose local taxes follow county, city and district lines (TX, FL, NY, VA, AZ, NM, IL, SC, CO, AL, LA, AK, PA, HI, MS, ID, the order of GEO_STATES). The address is placed on the map (see geocoding.html), PostGIS finds the outlines around it, and each outline's dated rate row is stacked by its type.

Sources: src/rates/map.ts, src/rates/shapes.ts, src/rates/types.ts, src/ingest/states/index.ts, src/ingest/states/tables.ts, src/ingest/states/sources.ts, src/ingest/states/*.ts (one adapter per state)

geoRateAt(state, point, date, street?, trace?)

  1. 502 if sales_tax_data_releases has nothing for the state; 422 if point is null.
  2. outlinesAt(state, point, date, "all", pad): the outlines in force on date; pad 0.003 degrees (about 300 m), or 0.06 when the state has any pj rows (hasRows).
  3. Load every rate row live on date; key them type:code, later starts_on winning.
  4. Refuse when: no county outline holds the point; the county has a no row; outside a rated city but within PJ_METRES (4,828 m) of a city with a pj row; inside a shape with a maybe row.
  5. rateOf(...) stacks the parts (below). No 45 row on the date is a 422.
  6. History check (below): with refuseBeforeFirstRate, refuse inside an outline that adds nothing on date though its rate starts on the release's first_listed day, after date.
  7. Edge check (below), then return { rate, parts, locationCode, files, alternatives }.

With a trace, every shape from step 2 is recorded (traceOutline, types.ts) before any refusal in step 4, so a refused address still shows its lines. After step 5, rateOf collects in levying the shapes whose rows it added, and those outlines get levies: true. The trace never changes the answer.

Levy types

Rows are (type, code) in sales_tax_jurisdiction_rates. leviesOf(shape, rates) picks which types a shape can carry: counties 00, rc; places and county subdivisions 01, 01x, x, 0c; districts any other type with their code.

Type Meaning
45 state rate
00 county, county-wide, unless a 01x city replaces it
01 city or town, added
01x city in place of its county (NY own-rate cities); city@county for a county-specific rate (LA towns in two parishes)
0c county's rate difference inside one city (AL), may be negative
rc county rate only outside every rated city (LA parishes; the code comment also cites NM, whose adapter uses x areas instead)
x exclusive area (TX city or combined area, IL and NM locations): replaces every other local rate
kx code area>kept: a jurisdiction an x area keeps, at this rate (TX)
addr code area\|house\|streetKey: one address's rate inside an x area (IL business districts)
no county refused (AL split counties)
pj police jurisdiction reaching 3 miles past a city, no outline (AL)
maybe unmapped district inside a city or parish, refused with both rates (LA; also emitted by alabama.ts and ttr.ts)
need need:x marker: every address must be in an x area, else refused (IL, NM)
other special district, inside its own outline

Stacking in rateOf: if any x area holds the point, the smallest by area wins; add it (or its addr row for this street), then each kx row it keeps, and stop. Otherwise add every levy, skipping 00 when a 01x city holds the point and rc when any rated city does; a city's @county row wins for that county. A city matched as both place and county subdivision counts once.

locationCode is the state code, then each part's code (without @county), joined by dashes.

Edges and margins (geocoding/index.ts, end of geoRateAt)

EDGE_METRES by geocode accuracy: rooftop 15, parcel 25, point 40, interpolated 75. marginOf(p) is p.metres when set (geocoders disagreed, see geocoding.html) else EDGE_METRES[p.accuracy].

For every levied shape whose edgeMetres < margin: pointsAcross(point, foot, edgeMetres, 2) gives a point 2 m past the nearest edge point (four points, one each way, when the address is on the edge); shapesHolding finds what holds it on date; rateOf is run for that side. If the rate differs, or the other side has no rate at all, the address is refused naming both rates.

The margin at a line is the point's (marginOf) plus the state's outlineMarginMetres (params.ts), for how far its loaded outlines may be from the state's own. Past that margin, within breakdownMarginMetres (60 m), a line is still read, but only for a breakdown: a different rate there is ignored, the same rate with other parts is listed in alternatives. The search radius (pad) reaches the wider of the two.

The same rate across the line settles the rate, not its parts. When the other side's parts differ (sameBreakdown, types.ts: the same part codes at the same rates), its breakdown is kept in alternatives and the answer's jurisdictions is uncertain (rates/index.ts). With breakdownMustAgree (params.ts) the address is refused instead, after one sharper point is asked for.

Dates and history

Every outline query reads the rows in force on the lookup's date (starts_on <= date <= ends_on): a loader keeps each edition it replaces (refresh.html), so a past date reads the lines of its time where an edition of them was loaded. The first edition loaded stands for every earlier date as well, since no older one is held.

A rate table can be incomplete in the past where an outline isn't: Texas's districts outside cities come from the current quarter's list only, so their rows start on that quarter's first day whatever their real start. The adapter says so (GeoStateData.ratesFirstListed, stored as sales_tax_data_releases.first_listed). ratedOnlyLater finds an outline holding the point that adds nothing on date, though a row for it that would apply there starts on first_listed, after date: inside an exclusive area, the area's kx row keeping it; elsewhere its own row. The address is refused: whether the district taxed on that date isn't known. Any other row's start is the publisher's, and before it there was no tax (a new Colorado district). On the boundary benchmark (scripts/tuning/boundary) this rule turns 20 wrong past-date Texas rates into refusals and costs 2 right ones.

Outlines (shapes.ts)

Function Does
outlinesAt(state, p, date, which, padDegrees) The one point-in-outline query every engine uses. st_dwithin on the GiST index, outlines in force on date (every family is dated); per outline: kind, fips, name, areaId, file, inside (st_covers), edgeMetres (distance to st_boundary on the spheroid), foot (st_closestpoint), area. which picks the family: all (every outline but held markers: the map engine and the range engine's Census step), indexed (verified area outlines and held: markers: indexedTaxAreas and California), zones (Missouri's and Utah's rp: zones). Each caller keeps only its decision rule. wholeZipRate (a ZIP's whole area against outlines) and nearbyRegions (raw tax_source_features, never a rate) ask other questions and keep their own queries.
shapesHolding(state, p, date) kind:fips of every shape in force on date covering a point
pointsAcross(...) flat-earth step past an edge (pure function)
outlineGeometry(state, outlines, p, metres, date) for display only (include=trace): each outline intersected with a square metres around the point, simplified to about 5 m (DISPLAY_SIMPLIFY_DEGREES), as GeoJSON with 5 decimals, keyed kind:fips
geometryOf(rings) SQL that turns rings into one valid multipolygon: polygonize the noded lines, keep faces inside an odd number of rings, dissolve seams, simplify to about 1 m (SIMPLIFY_DEGREES)

Invariant: each outline is stored as one dissolved multipolygon per (state, kind, fips) and edition (starts_on), so seams between pieces are never edges; on any date at most one edition of an outline is in force.

State adapters (geo-states/)

Each adapter is a GeoState { state, fetch(dir?) } returning GeoStateData { rates: GeoRateRow[], shapes, files: { rates, boundaries? }, boundariesFrom?, ratesFirstListed? }: boundariesFrom is the first day its outlines are in force where the source says (Texas's quarter), ratesFirstListed the day some of its rates are first listed (above). Shapes are the state's own outlines (kind county, place or district), keyed by the code their rate rows use. Census counties, places and county subdivisions load separately for every state.

Two ways to write one:

  • stateTable(state, load) (tables.ts): load returns { stateRates, locals, source, skipUnmatchedCities? }. Each local names its county or city as the state writes it (or by FIPS); censusCodes matches names to TIGER FIPS, exact then loose. A name that matches zero or several stops the load (or, with skipUnmatchedCities, skips a city with a warning). Used by VA, PA, FL, NY, HI, MS, ID and AL; SC wraps one and adds a Myrtle Beach district outline.
  • A custom GeoState that reads rates and outlines itself, as texas.ts (Comptroller rate files and ArcGIS boundary layers), illinois.ts, arizona.ts, new-mexico.ts, louisiana.ts, and ttr.ts (colorado, alaska from their lookup service). The lookup service dates its outlines (places.shapes.map takes a date): ttr.ts reads every outline on each day it reads rates (half-yearly from 2024 and today), and where one differs between two of those days finds the day it changed by halving the span, so each outline is loaded with the days it was in force (startsOn, endsOn; a source that dates its outlines replaces its whole history on load, refresh.html).

Helpers in sources.ts: fetchFile / fetchText (local copy in dir first, sends OPENTAXRATE_USER_AGENT, 120 s timeout), readXlsx, fetchLayer (ArcGIS pages to rings), ringsOf, bboxOf, isoDay, shiftDay, excelDay.

Adding a state

  1. Write src/ingest/states/<state>.ts exporting a GeoState, with stateTable if its rates follow Census names or FIPS.
  2. Give every row a type from the table above; dates as ISO, open end 9999-12-31.
  3. Add it to GEO_STATES in ingest/states/index.ts, which makes refreshAddressRates load its data and its TIGER outlines, and to MAP_STATES in src/coverage.ts, which makes addressRates route it to the map and lists it in /v1/coverage. test/coverage.test.ts fails if the two lists differ.
  4. Run refresh <ST> and check known addresses with check --cases.
  5. Update this note and ../state-coverage.html.
