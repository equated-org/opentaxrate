Design plan · proposed · equated-org/opentaxrate main · 2026-10-21

Precomputed tax regions in PostGIS

Move every outline into PostGIS and, at refresh time, cut each state into non-overlapping tax regions, one per unique set of jurisdictions, each dated and indexed. A lookup then becomes one indexed point-in-polygon query and one rate join, instead of fetching megabytes of JSON and stacking outlines in Node. The same change cleans the data enough to publish as a release asset, and replaces the geocoding and data sources whose terms block an open release.

Traced from src/engine/geo-lookup.ts, sst-lookup.ts, tiger.ts, load.ts and refresh.ts at commit 5b1d798, with timings and row counts from a database loaded with every state on 2026-10-21. Research on Stripe, TaxJar, geocoders, publishing and state terms done the same day.

Why

Today an address in a map state is placed by asking three outside geocoders, pulling every outline whose box is near the point out of Postgres as JSON, and testing them in TypeScript. For 901 Bagby St in Houston that is 977 ms of geocoding and about 320 ms of outline work over 2.5 MB of rings. The stacking rules (a city in place of its county, a Texas combined area that keeps some districts, an Alabama county's share inside a named city) all run per request, and a boundary edge check runs per request too.

The decision is to do that work once per release. When a state refreshes, its county, city and district outlines are overlaid into regions that each hold exactly one set of jurisdictions, its rate stack is resolved per date, and the result is stored as PostGIS geometry with a GiST index. A lookup is ST_Covers on that index and a join to the region's dated rates.

  • It's the shape Stripe built. Stripe Tax's jurisdiction resolution precomputes about 16,000 non-overlapping "places of taxation" in an R-tree and answers in a few milliseconds (Stripe engineering, 2025-07-10).
  • It moves 0.3 s to milliseconds. The index replaces the box query and the ray casting; the region carries its rate stack, so no stacking runs at lookup.
  • It makes the edge check exact. Distance to a region's boundary is one ST_Distance on geography, and the other side is simply the neighboring region.
  • It shrinks the data. 52,258 of 63,804 Census outlines are towns no rate refers to and disappear; outlines are simplified once; the shipped artifact is regions, not raw layers.

Out of scope: taxability, sourcing and product rules; replacing the street-range engine (the Streamlined states' own files stay authoritative there); a public hosted service.

What Stripe and TaxJar teach

Stripe's engineering post and TaxJar's API reference are the only detailed public accounts; Avalara publishes a precision scale and little else, and Anrok, Numeral and Kintsugi describe nothing. What carries over:

  • Precompute regions with time tags (Stripe, stated). Regions are recomputed per state when a boundary changes; old ones are kept and tagged so past transactions can be recalculated. Disjoint regions are split into parts ("Charleston alone consists of 73 disjoint areas").
  • Check topology (Stripe, stated). Boundaries "must be consistent with one another, meaning they border gaplessly and without overlaps." A load should fail on slivers and gaps.
  • Report precision, not just a rate (Stripe, stated). Stripe's address resolution returns address > street > postal_code > … plus the fields to collect for better precision; "street precision with no issues means every address on that street has the same tax rate."
  • Don't fall back silently (both). Stripe uses a ZIP centroid when it can't match; that's an approximation. OpenTaxRate refuses instead, and where a Streamlined state defines a fallback (North Carolina: the lowest combined rate in the ZIP+4), uses the state's own rule, because that is what its hold-harmless law protects.
  • Publish a support matrix (TaxJar, stated). TaxJar's changelog shows street-level accuracy arriving state by state in 2018 and lists the states where a street helps; Stripe lists 19 states where ZIP is unsafe. OpenTaxRate should publish, per state, its method, source and dates.
  • Measure accuracy and say how. Every vendor claims "rooftop" or "99.999%" without a method. OpenTaxRate's agreement checks against state lookups are the method; publish them per release.
  • Neither discloses near-boundary handling or which geocoder they use. The edge refusal has no public precedent; keep it, and document it.

Rules

  • Regions never overlap. Within a state and a validity span, every point is in at most one region; a load that produces overlaps or slivers above a set area fails.
  • A region is one set of jurisdictions. Two regions with the same set and touching are merged; a region in several pieces is one row, subdivided for the index.
  • Nothing is deleted. A boundary change ends the old regions (valid_to) and starts new ones, so any past date still resolves.
  • The state's own file wins. In the Streamlined states and Missouri, the address-range answer is authoritative; a region disagreeing with it is logged, not used.
  • Precision is part of the answer. Every response says address, street, zip4, postal_code or region, and, when refused, which input would settle it.
  • No default depends on someone else's goodwill. No public Nominatim, no undocumented state backend, no paid key is needed to run.

Workflows

Refresh builds regions

The operator runs docker compose run --rm refresh TX. Texas's rates and the Comptroller's layers load as today, then the overlay builds Texas's regions for each span its rates and layers cover.

Calls and SQLrefresh, map states 
clirefresh TX
└─ enginerefreshAddressRates()
   ├─ geo.fetch()                                 unchanged adapters
   ├─ loadGeoState()  → INSERT layers (ST_SimplifyPreserveTopology, ST_MakeValid)
   └─ addedbuildRegions(state)
      ├─ ST_Union(ST_Boundary(geom)) → ST_Polygonize      non-overlapping faces
      ├─ per face: point-on-surface → which layers hold it → jurisdictions[]
      ├─ merge touching faces with equal sets; ST_Subdivide large ones
      ├─ resolve rate stack per date span with today's rules  rateOf() moves here
      ├─ topology check: overlaps, gaps over 1 m², else fail
      └─ end previous release's regions, INSERT new ones + region rates

The operator sees one line per state with its region count and any topology failures.

A lookup reads one region

An app calls GET /v1/rate for 901 Bagby St, Houston, 2026-10-21.

  1. Address point. If the normalized address is in the address-point table, its precomputed region answers with precision: address and no geometry at all.
  2. Geocode. Otherwise the point comes from TIGER interpolation in PostGIS, then the Census geocoder, then any configured key (Geocodio).
  3. Region. ST_Covers on the regions index for the date; the region's rate is joined.
  4. Edge. If ST_Distance to the region's boundary is inside the point's margin and the neighbor region's rate differs, refuse with both.
The queryreplaces geoRateAt's fetch and stacking 
select r.id, rr.rate, rr.parts,
       st_distance(st_boundary(r.geom)::geography, p::geography) as edge_m
from sales_tax_regions r
join sales_tax_region_rates rr on rr.region_id = r.id
  and $date between rr.starts_on and rr.ends_on
where r.state = 'TX' and $date between r.valid_from and r.valid_to
  and st_covers(r.geom, p)            -- p = st_setsrid(st_point(-95.3694, 29.7602), 4269)

The app gets 8.25% with precision: address and region R-TX-0412 as the location code.

A release ships the data

Each quarter the maintainer tags a release. One export writes a Postgres dump for self-hosters and GeoParquet per table for analysts, plus a diff of changed rows.

  • Where. GitHub Releases (files under 2 GiB, no bandwidth limit) with an R2 mirror ($0 egress); a Zenodo copy per quarter for a citable DOI.
  • What's cleaned first. Census outlines no rate refers to (52,258 of 63,804) dropped; layers simplified and made valid; 1.31 million street ranges identical except dates merged; rows before the history floor dropped; Colorado and Alaska excluded until their terms are settled.
  • Not Dolt, for now. Dolt (Liquidata Inc. renamed to DoltHub in 2020) versions SQL tables with row diffs, but its Postgres flavor, Doltgres 1.0 (August 2026), has no PostGIS; the shipped diff files cover the same need.

Geocoding without the public services

Today's defaults break two providers' terms: the public Nominatim server's policy caps use at one request a second and says geocoding services must run their own; Mapbox's free results are "temporary" and can't be cached. The proposal makes the default self-contained and the keys optional.

  1. Own address points. The US DOT's National Address Database (about 90 million public-domain points from contributing states) and OpenAddresses where each source's license allows, normalized and matched in SQL like street ranges, each carrying its region.
  2. TIGER interpolation. The Census Bureau's address ranges in PostGIS (the TIGER geocoder extension, or the ranges loaded directly) for addresses the points miss.
  3. Census geocoder. Free and keyless, as a tie-breaker; it also returns county and place codes to cross-check the region.
  4. Optional key: Geocodio. 2,500 a day free, then $1 per 1,000; results may be stored; returns rooftop versus interpolated and county and place FIPS. Geocode Earth (hosted Pelias, storable with attribution) is the second choice. Mapbox only with permanent=true. Nominatim only at an endpoint the operator sets, never the public one by default.

Settling Colorado, Alaska and Nominatim

  • Colorado rates: replace now. The Department of Revenue publishes a half-yearly workbook of every jurisdiction's code and rate, home-rule cities included (Colorado_Jurisdiction_Codes_Rates_July-Dec2026.xlsx, archives to 2020). It replaces the lookup service's rate calls.
  • Colorado boundaries: ask, and rebuild meanwhile. The authoritative layer is the department's own GIS, with no download; the state just paused bulk lookups because they cost it $1.275 million a year. Email DOR_LocationFilers@state.co.us for a bulk export and redistribution terms, file an open-records (CORA) request for the layer, and meanwhile rebuild from DOLA municipal and special-district boundaries, counties, the RTD layer and the workbook's split codes, labeled approximate.
  • Alaska: rates from the Commission, boundaries from the state. The Remote Seller Sales Tax Commission's monthly workbooks give rates; the state's community boundaries (DCRA) plus Census boroughs give outlines. Email amstp@akml.org for its boundary records or how to become a certified database under its code's section 240.
  • Nominatim: no default. Require an endpoint; refuse to start against the public server without a contact in the User-Agent; throttle to one a second; cache; attribute OpenStreetMap.

Phases

  1. PostGIS and layers. Switch the image to postgis/postgis:17-3.5; add sales_tax_layers with geometry and GiST; load layers through ST_MakeValid and ST_SimplifyPreserveTopology; drop unreferenced Census outlines. Done when every map state reloads, and the Texas oracle check and the 29 tests still pass with lookups reading layers through ST_Covers.
  2. Regions. Add buildRegions(), region tables and the topology check; move the stacking rules from request time to build time; lookups read regions. Done when the Texas, Illinois and city checks agree as before, lookups are under 10 ms at p95, and no state has overlaps.
  3. Precision contract. Return precision and, on refusal, the input that would settle it; publish the per-state support matrix. Done when the API docs and coverage endpoint show both.
  4. Own geocoding. Load NAD (then licensed OpenAddresses) into address points with their region; add TIGER interpolation; make Nominatim opt-in and Geocodio the optional key. Done when the Illinois public-file check places at least as many addresses with no keys set as today with Mapbox.
  5. Terms and sources. Colorado rates from the workbook; Colorado and Alaska boundaries rebuilt from DOLA and DCRA; emails sent. Done when no adapter calls an undocumented backend.
  6. Release. scripts/release.ts cleans and exports dump, GeoParquet, diffs and manifest; CI runs the checks on the release. Done when a fresh restore.sh of the release answers the city checks.

Open questions

  • Overlay in SQL or in a build step? Recommended: in PostGIS (ST_Polygonize over unioned boundaries), so the build needs nothing beyond the database; fall back to GEOS in a worker only if a state is too slow.
  • Simplification tolerance? Recommended: 1 m, with the edge margin enlarged by the tolerance, so no answer changes by simplifying.
  • Keep raw layers in the release? Recommended: yes in GeoParquet for analysts, no in the dump, which needs only regions.
  • Streamlined states into regions too? Recommended: not now; their address files are authoritative and already fast, and regions there would only back the map step.
  • Public now or after phase 5? Recommended: after phase 5, when nothing depends on terms we haven't settled.

Appendix: terms

Tax region

A piece of a state where every point owes the same set of jurisdictions; Stripe calls these places of taxation.

R-TX-0412 = {state 48, City of Houston 2101017, METRO 3101990}
→ 6.25% + 1% + 1% = 8.25%

PostGIS and GiST

The spatial extension for Postgres and its tree index for shapes.

create index on sales_tax_regions using gist (geom);
select id from sales_tax_regions where st_covers(geom, st_setsrid(st_point(-95.37, 29.76), 4269));

Overlay

Cutting overlapping outlines into faces that don't overlap, then labeling each face with the outlines it lies in.

faces = st_polygonize(st_union(st_boundary(geom)))
face.jurisdictions = layers where st_covers(layer.geom, st_pointonsurface(face))

Geocodio

A US/Canada geocoding company whose terms let you store results; it says whether each point is rooftop or interpolated and can return county and place FIPS.

GET api.geocod.io/v1.9/geocode?q=901 Bagby St, Houston TX&fields=census
→ accuracy_type "rooftop", county_fips "48201"

Nominatim

OpenStreetMap's open-source geocoder. Anyone can run it; the public server at nominatim.openstreetmap.org is for light use only.

policy: ≤ 1 request/second, identify your app,
cache results, no bulk, geocoding services run their own

NAD

The US Department of Transportation's National Address Database: public-domain address points contributed by states and counties, about 90 million in release 19.

AddNo_Full "901", StNam_Full "Bagby Street", Zip_Code "77002",
Longitude -95.3694, Latitude 29.7602, Placement "Rooftop"

Precision

How exactly the answer is placed, so a caller knows whether to trust or ask.

address > street > zip4 > postal_code > region > refused
refused → { needs: ["line1"] }

Hold harmless

State law protecting a seller who relied on the state's own rate and boundary data from penalties for its errors.

NC G.S. 105-164.42L: not liable for underpayments from erroneous information
in the Secretary's databases until 10 business days after notice
